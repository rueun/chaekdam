## 2. 아키텍처 제약을 둔다

### 프롬프트 엔지니어링 vs 하네스

> **프롬프트 엔지니어링과 가장 크게 갈리는 지점**

- **하네스**: 좋은 코드를 **기계적으로 강제**.
- **프롬프트**: 좋은 코드를 **짜달라고 말함**.

### 구체 원칙

- 구현 방식은 세세하게 지시하지 말되 **반드시 지켜야 할 규칙은 기계적으로 강제**한다.
- **문서가 아니라 구조적 테스트로 강제**하여 규칙 위반 시 즉시 에러 → **잘못된 코드 통과 불가**.
- **제약을 걸면 걸수록 에이전트 생산성이 올라간다.**
  - 자유도가 너무 놓으면 이것저것 탐색하다가 헤맨다. 선택지를 줄여주면 오히려 정답에 빠르게 수렴한다.

## 3. 피드백 루프

### 왜 필요한가

- **AI 는 자기 결과물을 스스로 제대로 평가하지 못한다.** → Anthropic 연구
- 품질이 떨어져도 "잘했다" 고 **자신있게 답하는 경향**이 있다.

### 외부 검증 장치

에이전트가 자기 작업을 외부 기준으로 검증할 수 있는 장치 필요.

| 장치                 | 역할                                                               |
| -------------------- | ------------------------------------------------------------------ |
| **자동 테스트**      | 코드 → 즉시 검증                                                   |
| **타입 체크 & 린터** | 규칙 위반 → 즉각 피드백                                            |
| **프리커밋 훅**      | 저장 전 자동 검사                                                  |
| **검증 다각화**      | 코드 작성 모델과 검증(리뷰, 테스트) 모델을 **다른 걸로 사용**한다. |

→ **린터 빨간 불 → 에이전트가 스스로 수정 → 사람 개입 불필요**.

## 4. 엔트로피 관리 (가비지 컬렉션)

### 문제

- 코드 많이 생성 → **코드베이스 무질서 축적**
  - 문서와 코드 불일치 발생, 중복 코드, 미사용 파일
- 방치하면 에이전트의 작업 품질 **지속 하락**. → 참고하는 기존 코드 자체가 엉망이기 때문.

### 해결

**정리 전담 에이전트를 주기적으로 가동**:

- 문서-코드 일치 검사 에이전트
- 아키텍처 규칙 위반 탐지 에이전트

## 5. 핵심 원칙 5가지

### 1️⃣ 모델을 바꾸지 말고 환경을 바꿔라.

- 결과물이 좋지 않을 때 "더 좋은 모델을 써야지" → **잘못된 접근**
- 같은 모델이라도 **하네스 설계에 따라 결과가 완전히 달라진다.**

### 2️⃣ 실패에서 시작하라.

- **완벽한 시스템을 미리 설계**하려 하면 안된다.
- 에이전트 실행 → 실패 시, **구조적 방지 장치 추가**.

### 3️⃣ 적게 넣어라.

- 규칙을 너무 많이 넣으면 **오히려 성능 저하.**

### 4️⃣ 말로 하지 말고 시스템으로 강제하라.

- 프롬프트 → 에이전트가 **무시 가능**
- 시스템 제약 → **무시 불가.**
  - 린터, 테스트, CI 같은 도구들로 규칙 강제화.

### 5️⃣ 하네스도 진화한다.

- 모델 발전에 따라 **멀티 에이전트 3개 → 싱글 에이전트**
- 한 번 만들고 끝이 아니라 **모델과 함께 계속 진화**시켜야 한다.

## 7. 훅 (Hooks)

- 코드 저장 직전 자동 실행 → 에러 있으면 Claude 한테 돌려보낸다. (타입 검사 및 문법 검사 수행)
  - **사람 개입 없이 스스로 수정 가능.**
- **"잘 짜줘" 부탁이 아니라 못짜면 저장 자체가 안되는 구조.**
