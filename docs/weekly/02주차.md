## 1. AI 페르소나 정책 단순화

### 변경 전 (1주차 결정)

- 페르소나 = 선택형 일반 페르소나 + **사망 작가 페르소나**
- 작가별 큐레이션 파일 (`ai-prompts/personas/hesse.md` 등) 작성 예정

### 변경 후 (2주차)

- 페르소나 = **범용 톤 카테고리만** (학구파 / 캐주얼 / 비평가)
- 작가 페르소나 V1 제외 — Claude 가 이미 책·작가·문체를 알고 있다고 가정
- 작가별 큐레이션 파일 폐기 — `ai-prompts/personas.md` 단일 파일로 통합

### 이유

- **단순화** — 페르소나 폭발 방지, 시스템 프롬프트 관리 비용 ↓
- **저작권·인격권 리스크 회피** — 작가 페르소나 자체 제외
- **검증 우선** — 범용 페르소나로 사용자 반응 검증 후 작가 페르소나 도입 여부 재결정
- **Claude 자체 지식 활용** — 별도 큐레이션 없이도 책 컨텍스트에서 톤 풍부

### 영향

- ADR-009 갱신
- PRD §AI 페르소나 정책 단순화
- ARCHITECTURE.md `Persona` 엔티티 정의 단순화

## 4. 도메인 모델 핵심 결정

### 11개 엔티티

`User` · `Participant` · `Book` · `Author` · `Persona` · `ReadingNote` · `Discussion` (Aggregate Root) · `Message` · `Reflection`

### Aggregate 경계

- **Discussion** = Discussion + Participants + Messages (트랜잭션 단위)
- **ReadingNote**, **Reflection**, **Book**, **Persona**, **User**, **Author** = 독립 Aggregate
- Aggregate 간 참조는 ID 로만

### Specification (RLS 와 이중 방어)

- `CanReadDiscussion` (참가자 검증)
- `CanWriteReadingNote` (소유자)
- `CanWriteReflection` (참가자 + status COMPLETED)
- `CanReadReflection` (작성자)

### 도메인 이벤트

`DiscussionStarted`, `MessageAdded`, `DiscussionCompleted`, `DiscussionAbandoned`, `ReflectionWritten`, `ReadingNoteCaptured`

## 5. 데이터 모델 — Supabase 스키마

### 테이블 10개

`users` · `authors` · `books` · `personas` · `reading_notes` · `discussions` · `discussion_notes` · `participants` · `messages` · `reflections`

### RLS 정책 핵심

- 본인 소유: `reading_notes`, `reflections` (`auth.uid() = user_id`)
- 참가자만: `discussions`, `messages`, `participants`, `discussion_notes` (participants 조인 검증)
- 공유 데이터: `authors`, `books`, `personas` (모두 SELECT, 관리자만 INSERT)

### 시드 데이터

기본 페르소나 3개 (`STUDIOUS` / `CASUAL` / `CRITIC`) — `supabase/seed.sql`

### 마이그레이션 순서

`0001_users.sql` → `0009_triggers.sql` 까지 9개 순차 적용

## 6. AI 시스템 프롬프트 구조 (하이브리드 모드)

### 시스템 메시지 = 3개 블록

1. **페르소나 시스템 프롬프트** (캐싱)
2. **책 메타데이터 블록** (캐싱)
3. **운영 가드레일** (캐싱) — 언어·길이·내용·형식

### 첫 사용자 메시지

사용자가 올린 노트 1~3개를 마크다운 인용(`>`)으로 묶어 전달.

### 토큰 추정

- 시스템 (캐싱) 약 850 토큰
- 토론 5~10턴 약 5,000~15,000 토큰
- 프롬프트 캐싱으로 입력 비용 ~50% 절감 예상

### 가드레일 핵심

- 책 결말·반전 스포일러 금지 (사용자가 먼저 언급 X)
- 책 텍스트 인용은 사용자 노트 범위만 (저작권)
- 사용자 의견 단정 부정 금지
- 응답 200~500자 내외

## 8. 핵심 학습

### 도메인 모델링이 코드 기반

- ARCHITECTURE.md 의 표 1줄 → domain-model.md 의 풀 명세 1섹션
- 엔티티 필드·정적 팩토리·도메인 메소드·불변 규칙·상태 전이까지
- 이게 그대로 `lib/domain/` 코드의 가이드

### 권한 검증 이중 방어 (ADR-004) 가 실전에서 어떻게

- DB 레벨: RLS 정책 (1차)
- 도메인 레벨: Specification 객체 (2차)
- 둘 중 하나만 있으면 백엔드 분리 시 큰 비용

### 하이브리드 모드 = 비용·깊이 균형

- 책 메타 (시스템 메시지, 캐싱) + 사용자 구절 (가변)
- 책 전체 주입은 비용 폭증, 구절만은 빈약
- 프롬프트 캐싱이 하이브리드의 비용 절감 핵심

### Feature Spec 이 구현 가이드

- "기능 시작 전 입출력·예외·UI 상태"를 미리 정리하면 코딩 방황 줄음
- zod 스키마 정의 → Server Action 검증 → 도메인 검증 흐름 일관
